# AI 业务调试台使用手册（业务人员）

## 1. 适用范围与最重要的安全边界

AI 业务调试台用于维护三类业务对象：

- **Skill（技能）**：提示词、表单声明、资料、数据文件、脚本及工具声明。
- **专家**：引用一个或多个已发布 Skill，并定义角色、规则和能力边界。
- **专家团**：引用多个已发布专家，指定主协调专家，并定义成员协作与转交规则。

业务人员的日常目标是：在测试环境完成调试后，交付一个已发布专家团导出的**完整专家团 ZIP 包**。

> [!CAUTION]
> **不要由业务人员操作“生产暂存导入”或“生产部署”。**
>
> 这两个区域连接生产环境。生产暂存导入虽然不会立刻切换正式会话，但会把包写入生产部署历史；生产部署的激活、恢复、回滚或下线会影响正式新会话所使用的专家团快照。只有经变更确认、具备生产操作权限的发布/运维人员才能执行，并且必须先核对专家团 ID、名称、版本、包哈希和变更内容。

业务人员通常只需要完成“编辑 → 调试 → 发布 → 导出专家团 ZIP”，再将 ZIP 和测试结论交给发布负责人。

## 2. 先理解：修订、发布与生产生效不是同一件事

| 名称 | 含义 | 是否影响正式对话 |
| --- | --- | --- |
| 修订 `r1/r2/...` | 每次保存生成的候选配置，可继续编辑和调试。 | 否 |
| 发布 `v1/v2/...` | 已完成调试、人工确认后的不可变版本。 | 否 |
| 专家团 ZIP | 从一个已发布专家团导出的完整依赖闭包，是跨环境交付物。 | 否，直到生产被确认激活 |
| 生产部署 | 将生产暂存区中经确认的专家团 ZIP 激活为正式新会话配置。 | 是 |

因此，**工作台中的“发布”不等于正式环境生效**。不要把本地/测试环境的“当前发布”当作生产部署。

## 3. 登录与界面说明

1. 打开 AI 业务调试台，填写自己的用户名进入。
2. 在右上角选择“白天”或“夜间”主题；偏好仅保存在当前浏览器。
3. 左侧对象库按 Skill、专家、专家团筛选；可搜索名称或 ID。
4. 工作区常用区域包括：
   - **业务对象工作区**：创建、编辑、保存修订、查看依赖和版本。
   - **调试与效果验证**：候选修订手动测试、测试记录、批量用例与人工确认。
   - **发布中心**：查看已发布版本、导出 ZIP；其中的生产暂存/生产部署仅供授权发布人员使用。

## 4. 创建和编辑对象

### 4.1 Skill

Skill 是最底层配置。可编辑 Prompt、运行契约、表单、引用资料、数据文件、允许的脚本与能力声明。

- 资料、`references/`、`assets/`、`scripts/` 等文件会随修订保存。
- Python 脚本会经过安全校验；未通过时可以保存候选修订，但不能发布。
- 修改 Skill 后，不能直接认为上层专家和专家团已经更新；必须按第 6 节的逐层流程重新发布。

### 4.2 专家

专家需要选择一个或多个**已发布的 Skill 版本**作为锁定依赖，并填写专家规则。

必须填写对象级 **Brief**：

- 面向最终用户的一行简介，1–120 字。
- 例如：`为学生提供留学路径、院校选择和申请准备建议。`
- Brief 会随修订、发布、导出 ZIP、生产快照和 SSE 状态流转，并用于专家卡片、工具栏等用户展示。

### 4.3 专家团

专家团需要选择至少两位**已发布的专家版本**，并指定其中一位为主协调专家。

请分别维护两类摘要：

| 字段 | 用途 | 示例 |
| --- | --- | --- |
| 专家团 Brief | 面向用户介绍整个专家团，1–120 字。 | `覆盖学习、升学、留学与职业探索的学生成长专家团。` |
| 成员 `routing_brief` | 仅供主协调专家判断应分流给谁，不是用户介绍。 | `国别选择、申请条件、院校专业、申请时间线。` |

转交卡的说明文案优先取**目标专家对象的 Brief**；该 Brief 缺失时才回退取成员 `routing_brief`，两者都为空时才展示本次转交原因。

## 5. 保存、调试与发布

每次编辑完成后遵循以下流程：

1. 点击保存，生成新的候选修订 `rN`。
2. 检查修订校验结果；尤其确认 Brief、依赖版本、脚本安全校验均通过。
3. 在“候选修订手动测试”中使用真实问题验证回答、表单、资料、脚本和专家转交。
4. 如有条件，补充批量测试用例并人工确认。
5. 选择已完成的调试记录作为证据，勾选人工确认后发布，得到不可变版本 `vN`。

发布后不要直接覆盖或删除旧版本。需要恢复时，应由负责人把“当前发布”切换到已验证的历史版本；这不会删除较新的版本。

## 6. 修改任意一个 Skill 后，必须重新交付专家团包

即使只改了一个 Skill，也必须完整走完以下闭环：

```text
修改 Skill
  → 保存、调试、人工确认、发布 Skill 新版本
  → 更新引用它的专家：选择该 Skill 新发布版本
  → 保存、调试、人工确认、发布专家新版本
  → 更新引用该专家的专家团：选择该专家新发布版本
  → 保存、调试、人工确认、发布专家团新版本
  → 从该专家团发布版本导出完整专家团 ZIP
```

原因是专家和专家团会锁定**精确的下游发布版本**。只发布 Skill 新版本不会自动改变已经发布的专家或专家团，更不会自动改变任何生产部署。

> [!IMPORTANT]
> 对外交付时不要单独交付 Skill ZIP 或专家 ZIP，也不要手工把旧包与新文件拼接。
>
> 必须从最终已发布的**专家团版本**导出 ZIP。系统会递归打入该专家团、成员专家、锁定 Skill、资料、脚本、依赖锁和哈希，形成唯一完整交付包。

## 7. 如何导出最终交付包

1. 打开“发布中心”。
2. 找到目标专家团的已发布版本，确认名称、`expert_team_id`、版本号和依赖版本正确。
3. 点击“导出”。
4. 保存生成的 `expert_team` ZIP，并建议文件名包含：专家团 ID、发布日期、版本或包哈希。
5. 将下列内容交给发布负责人：
   - 专家团 ZIP；
   - 专家团 ID、名称和发布版本；
   - 本轮变更摘要（改了哪些 Skill/专家/规则/资料）；
   - 手动测试或批量测试结论；
   - 已知限制、回退建议和负责人。

交付前检查 ZIP 的根对象必须是 `expert_team`，而不是只包含 `TEAM.md + team.yaml` 的浅层包。

## 8. 生产暂存导入与生产部署：仅授权发布人员操作

以下内容是为了让业务人员理解交付后的流程，**不是日常操作指引**。

### 8.1 生产暂存导入

发布负责人收到专家团 ZIP 后，先在生产环境的“生产暂存导入”上传。

- 导入会校验 ZIP 清单、文件哈希、依赖闭包、能力声明和脚本安全性。
- 导入成功后只形成 `staged` 暂存记录，尚未切换正式新会话。
- 仍须在上传前确认：包来源可信、专家团 ID 正确、测试结论完整、变更已获批准。

### 8.2 生产部署/激活

只有在完成变更确认后，授权发布人员才可激活暂存部署。

- 激活后，**新建正式会话**使用该 ZIP 固化的专家团快照。
- 正在生成的回答会完成；已有会话在下一次用户操作时按系统规则同步新配置。
- 同一个 `expert_team_id` 的新部署会替换当前活跃部署；名称只用于展示，不决定替换身份。
- 生产部署支持回滚、恢复与下线，均应由发布负责人按变更流程执行。

## 9. 不建议业务人员执行的操作

- 生产暂存导入、生产部署激活、回滚、恢复、下线。
- 永久删除对象：它会删除对象、修订、发布版本和资产，虽然生产已激活 ZIP 不会被改写，但仍会影响工作台对象库与后续维护。
- 修改对象 ID：这是创建后继草稿的安全迁移流程，需要重新调试、发布并逐层迁移引用。
- 在未完成测试时把候选修订当作发布版本导出或交付。

如确有需要，请先由业务负责人确认影响范围，再交由具备权限的配置管理员或运维人员处理。

## 10. 交付前检查清单

- [ ] 改动的 Skill 已保存、调试、人工确认并发布。
- [ ] 受影响的专家已锁定新的 Skill 发布版本，并重新调试、发布。
- [ ] 受影响的专家团已锁定新的专家发布版本，并重新调试、发布。
- [ ] 专家与专家团均填写了合规的 Brief；成员 `routing_brief` 已覆盖需要分流的专项领域。
- [ ] 已验证主协调专家、专家转交卡、表单、资料和脚本等关键路径。
- [ ] 最终导出的是已发布专家团的完整递归 ZIP。
- [ ] 已提供变更摘要、测试结论、专家团 ID 和回退建议。
- [ ] 未由业务人员执行任何生产暂存导入或生产部署操作。

## 11. 常见问题

### 我只改了一句话的 Skill，需要重新导出专家团吗？

需要。Skill 新版本不会自动写入已发布的专家和专家团。必须重新发布受影响专家和专家团，再从最终专家团导出完整 ZIP。

### 发布了工作台版本，正式对话为什么没有变化？

工作台发布只生成测试/本地可调试的不可变版本。正式新会话只有在授权人员将专家团 ZIP 暂存导入并确认激活后才会变化。

### 转交卡为什么没有显示我填的 `routing_brief`？

转交卡优先展示目标专家的对象级 Brief。`routing_brief` 用于协调专家的分流；只有专家 Brief 缺失时才作为卡片说明回退使用。

### 能否把单个 Skill 包直接上传到生产？

不应这样做。生产交付根对象必须是完整专家团包，以确保专家、Skill、资料、脚本和依赖版本是同一套可追溯快照。
