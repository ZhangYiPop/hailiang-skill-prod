# 对话 Harness 最终升级目标与实施计划

日期：2026-10-09（Asia/Shanghai）  
状态：目标与计划已整理；本文不代表代码改造已完成。

## 1. 最终定位

本项目升级为一套对话 harness：围绕模型构建可靠的对话执行环境，统一管理模型调用、工具执行、任务规划与调度、上下文、事实、用户输入请求、挂起恢复、事件和结果验证。

专家团是 harness 的一种运行模式。主 agent 规划和拆解任务，授权专家作为 subagent 承担独立子任务；独立任务可并行，有依赖的任务按依赖推进。harness 执行确定性的状态迁移和权限校验，agent 负责语义判断、规划与业务分析。

最终体验：用户在一个对话中提出目标，专家各自分析；需要信息的专家通过工具提出问题并挂起，其他专家继续工作；用户在气泡内按专家分类的卡片中回答；对应专家从原工具调用继续执行，可多轮追问；主 agent 根据任务结果、依赖和待补充信息进行阶段反馈与最终汇总。

## 2. 用户问题与目标追踪

| 编号 | 用户问题或明确要求 | 升级目标 |
|---|---|---|
| U01 | 项目能否变成 subagent 专家团 | 保留专家包与 Skill 基础，增加独立子任务执行环境 |
| U02 | 主 agent 规划、拆解并选择专家，可并行 | 结构化计划、授权分派、依赖图和有界并发 |
| U03 | 专家需要补充信息时挂起，其他专家继续 | 子任务独立等待和恢复，等待不占用模型请求或执行线程 |
| U04 | 气泡内小对话框，支持表单或文字 | 受控输入 schema 与文字输入卡片 |
| U05 | 多专家同时追问，按专家分类；同专家多轮追问 | 独立输入请求、专家任务分组、轮次与历史答案 |
| U06 | 补充答案是否需要新接口，而不是 chat | 独立答案提交语义，精确恢复原工具调用 |
| U07 | 追问、Skill 本地资料搜索、Web Search 都是 tool | 统一工具协议，支持即时、后台与等待用户的执行方式 |
| U08 | 最近对话之外什么会影响回复和指令遵循 | 可解释的上下文投影与完整调用追踪 |
| U09 | 多轮上下文与事实如何管理 | 会话、子任务、输入请求分层；事实统一管理与版本化 |
| U10 | 冗余策略是否导致重复追问、指令遵循差 | 收敛规则和状态来源，验证重复追问及对话推进质量 |
| U11 | 最终其实要一套 harness 的对话 | harness 为总体架构，专家团为其运行模式 |

## 3. 当前代码评估与证据边界

以下是代码层面的已确认现状，不是生产会话质量评测结论。

| 现状 | 代码入口 | 含义 |
|---|---|---|

| 实际仍选择一个活动专家 | `agentscope_expert_runtime.py::handle_message` | `member_runs` 和 `delegation_trace` 仍是预留空值，未实现并行子任务 |
| 已有追问工具 | `agentscope_expert_runtime.py::_request_declared_form` | 目前转交 native questionnaire，不是通用的持久化工具挂起机制 |
| 已有气泡内表单 | 前端 `FactFormBlock.tsx`、`MessageBlocksRenderer.tsx` | 可以复用控件，需新增专家任务分组及多轮交互 |
| 表单最后仍作为普通消息发送 | 前端 `useChatActions.ts::handleSubmitFactForm` | 调用 `handleSendMessage(followupMessage)`，需改为工具答案提交 |
| 同一会话以当前 generation 控制输出和保存 | `core/concurrency.py::TurnCoordinator` | 不能给每个专家直接启动现有会话 turn，否则可能互相替代 |
| 已有统一上下文 v3、事实去重和问答账本 | `docs/unified-context.md`、`fact_prompt_projection.py`、`question_progress.py` | 保留已有效的机制，继续统一各调用路径 |
| 路由与直答的上下文覆盖不同 | 专家路由显式注入 `question_answer_context`，直答有另一套 prompt | 需使用一致的事实和问答状态投影；不同阶段只追加必要指令 |
| 团队提示词禁止自动转交 | `agentscope_expert_runtime.py::_run_agent` 中团队规则 | 与自主分派目标冲突，需要按新运行模式更新 |
| 平台、专家、Skill、记忆均有规则 | `skill_runtime/session.py`、专家运行时、Soul 与 Skill 文档 | 存在规则分散、优先级张力和注入不一致风险 |

当前已包含去重、事实来源约束和重复回复检查，不能笼统认定所有策略都冗余。重复追问可能来自状态未同步、事实未落库、上下文缺失、指令冲突或输出处理。具体根因需要检查最终 messages、工具定义、工具结果和原始/最终输出。确定性测试通过不等于真实模型对话质量达标。

## 4. Harness 的职责与模块

| 模块 | 职责 |
|---|---|
| Conversation Service | 接收普通对话意图、关联用户与孩子档案、管理会话 |
| Plan / Task Scheduler | 校验计划、维护依赖、调度和取消子任务、限制并发及预算 |
| Agent Runner | 组装上下文、调用模型、分派工具、保存检查点、恢复执行 |
| Tool Runtime | 工具注册、授权、schema 校验、执行状态、错误和结果协议 |
| Input Request Service | 问题发布、答案校验、幂等提交、过期处理及恢复通知 |
| Context Composer | 从权威状态生成每次调用所需的统一上下文投影 |
| Fact Service | 事实归属、来源、版本、冲突、派生依赖与变更事件 |
| Event / Checkpoint Store | 持久化状态、恢复任务、推送进度、事件重放与调用追踪 |
| Reply / Evaluation Layer | 区分生成失败与业务缺信息，记录验证、重试及真实质量评测 |

实施可以继续放在现有后端中，模块边界不要求拆成多个服务。模型框架或 SDK 的最终选择通过恢复能力验证后决定，不在本目标中假定现有 AgentScope 自动支持全部能力。

## 5. 任务与工具生命周期

基本对象：`session_id`（对话）、`team_run_id`（一次整体任务）、`agent_task_id`（专家子任务）、`execution_id`（一次执行尝试）、`tool_call_id`（模型工具调用）、`input_request_id`（一次追问）。同一专家可承担多个子任务，不能只用 `expert_id` 作为状态隔离键。

子任务状态：`queued → running → waiting_for_user → queued → running → completed`；另有 `waiting_for_dependency`、`failed` 和 `cancelled`。有效状态迁移由 harness 校验。主任务状态和子任务状态分开；主任务可同时有运行中的专家和待答问题。

工具统一包含调用标识、所属任务、参数、授权、状态、结果/错误和幂等信息。工具类别包括：

- `request_user_input`：创建输入请求并持久化检查点，挂起对应子任务。
- `search_skill_assets`：按关键词搜索当前角色授权 Skill 的本地 references/assets 片段及出处；这是 Skill 资料搜索工具，不代表项目已有独立 RAG 服务。旧运行中挂起的 `rag_search` 调用仍可恢复。
- `web_search`：返回搜索资料、出处和时间信息。
- `read_facts` / `propose_fact_updates`：受控读取与建议更新事实。
- `delegate_tasks`：供主 agent 分派授权专家，校验任务范围和依赖。

等待用户不能只返回一段“请等待”文字让模型继续生成。runner 必须在明确边界停止执行、释放资源，保留待完成的工具调用。收到答案后作为该工具调用的结果接续执行；保留已完成工具结果，避免从头重跑。检查点保存可序列化消息、任务状态、预算及工具调用，不要求保存模型内部推理过程。

工具支持失败、超时、取消和有限重试。检索类重试与有副作用工具的重试分开处理；后者必须有幂等或结果核对机制。正常聊天允许修改目标、继续、取消或另起任务，由主任务控制语义处理，不能默认取消所有专家。

## 6. 答案接口与气泡卡片

推荐新增：`POST /api/v2/sessions/{session_id}/input-requests/{request_id}/answers`。

请求提供 `submission_id`、`expected_version`，以及结构化 `answers` 或自由文字 `text`。服务端根据请求记录定位子任务和原工具调用，校验用户/档案归属、请求状态和输入结构，不相信客户端任意指定的专家身份。重复提交返回同一提交结果；过期、取消或旧版本请求不能恢复旧执行。

答案保存、输入请求状态更新和可靠恢复通知在事务或等价机制中完成。提交返回已接受及任务状态；专家结果通过统一事件流推送。普通 chat 继续承担新意图和对话，补充答案有独立业务语义；若使用同一物理入口，必须有独立 action 和处理链，不能转换成普通聊天文本。

前端按专家及子任务分组，在消息气泡内显示输入卡片。支持单选、多选、数字、文字等受控字段；同一专家第 N 轮追问独立标识。各卡片独立草稿、提交、错误、已答和失效状态。历史答案可回看，新增追问产生新请求；刷新页面或断线重连恢复状态。用户回答一个专家时，其他专家不受影响。相同共享问题可以关联多个等待任务，明确回答后按各任务需要恢复，避免重复询问。

## 7. 多轮上下文管理

会话层保存总体目标、计划、相关共享事实及专家状态/结果摘要；子任务层保存自己的任务、对话、工具结果、检查点和未解决事项；追问层保存问题、轮次、答案及工具关联。

每次模型调用由同一 composer 输出：公共平台规则、专家规则、当前任务目标/完成条件、相关有效事实及版本、执行与问答进度、旧任务摘要、近期消息、本轮输入/工具结果、当前所需检索片段。路由、直答和 Skill 执行共享同一事实与问答投影，再附加各自必要指令。

使用 token 预算，轮数是辅助限制。压缩旧消息并保留原始记录与来源引用；长工具输出存原文、按需投影片段。摘要保存目标、约束、决策和未完成事项，不能成为唯一事实库；不能将旧摘要中的值重新覆盖已更正事实。挂起工具调用及恢复信息完整保存，不被摘要替代。其他专家的完整历史默认不注入，仅按依赖传递结果摘要和必要证据。

集中管理平台规则的优先级和版本，避免多个片段各自声明最高优先级。事实和检索内容作为数据与证据处理，不能因为嵌入提示词而获得指令权限。记录最终调用上下文各部分来源、版本、裁剪情况和 token 估算，以解释某次回复。

## 8. 事实管理

沿用用户级、孩子档案级、会话级事实，增加主任务/子任务局部事实。明确孩子归属，防止跨档案混用。用户临时选择和本次计算假设不自动升级为长期档案。

事实包含字段、值、范围、对象、来源、状态、记录时间、适用时间、版本、替代关系；来源关联用户消息、输入答案或工具结果。区分用户明确陈述、待确认候选、派生结果、外部资料和已失效记录。“用户确认”表示来源已确认，不表示外部客观真实性已核验。模型置信度不能自动把推断变为确认事实。

专家提出变更，统一事实服务校验与落库。结构化答案按服务端字段映射直接校验；自由文字提取保留原文证据和歧义。明确更正更新当前版本并保留历史；冲突先核对时间、口径和对象，不采取任意最后写入覆盖。

每个任务记录所使用的事实版本，派生结果记录依赖。共享事实更新发出事件；运行任务在执行边界检查相关变化，已完成结果按依赖标记需复核。仅影响相关任务，不默认重启全团。共享答案可供适用任务读取，专家局部假设和未确认判断不得自动传播为事实。

## 9. 重复追问与指令遵循的升级目标

统一问题账本记录 pending、answered、skipped、expired 等状态，区分明确未回答、回答无效、不知道与拒绝补充。对应问题完成后同步事实及任务状态。平台公共规则集中，业务指令归专家和 Skill；保留必要验证，减少多处同义补丁。

`request_user_input` 执行前校验已知答案：适用答案已存在则返回已有证据让专家推进；信息存在冲突、过期或用户要求更新时允许澄清，并记录原因。禁止以模型生成失败作为“用户缺信息”的依据。禁止靠无限重试解决重复问题；预算用尽进入可观察的失败或受限状态。

验收需同时覆盖指令执行、连续任务推进、已回答问题不重复、用户更正、意图切换以及拒绝补充。语义相似问题不能只靠精确字符串比较判定，应结合字段/问题标识、证据和人工复核。真实质量改善通过同模型、同配置的基线对话与升级后回放比较，记录失败样例、重复追问次数和任务完成情况；数值阈值由基线测量后确定，不虚构改善百分比。

## 10. 实施阶段与交付物

| 阶段 | 工作 | 完成证据 |
|---|---|---|
| P0 基线与规则审计 | 采集问题对话、最终 prompts/工具日志；盘点规则和状态来源；确定统一协议 | 可复现基线、规则清单、数据模型/API/事件规范 |
| P1 Harness 基础 | 独立任务、工具运行协议、检查点、输入请求与答案接口、恢复调度 | 单专家追问→回答→恢复→再次追问，进程重启后可恢复 |
| P2 上下文与事实收敛 | 统一投影、回答账本、事实版本/冲突/依赖、追问前校验 | 各调用看到同一版本；旧摘要不回填更正值；已答不重问 |
| P3 专家团调度 | 主 agent 结构化计划、授权分派、依赖、有界并发、取消及汇总 | 两专家并行，单个等待不阻塞其他专家，有依赖任务正确启动 |
| P4 气泡交互与检索 | 专家分类卡片、多轮记录、独立提交、统一事件重放；Skill 本地资料搜索/Web Search tools | 多卡片同时交互、刷新恢复、原工具接续、检索来源可追踪 |
| P5 迁移与质量验证 | 数据迁移与兼容、部署恢复验证、真实模型对话回放、预算与失败评测 | 下表验收全覆盖，记录剩余限制与迁移方案 |

阶段安排只是实现顺序，不能以单专家 MVP 或保留单一活动专家作为最终完成状态。P1 即需提供最小输入卡片以验证完整链路，P4 再完善专家分类体验。

## 11. 最终验收清单

| 编号 | 场景 | 必须观察到的结果 |
|---|---|---|
| A01 | 主 agent 接到需要多专家的任务 | 结构化拆解、授权专家分派、依赖与完成条件可追踪 |
| A02 | A 专家追问，B 专家仍运行 | 仅 A 等待；B 可检索、分析并输出阶段结果 |
| A03 | A、B 同时追问 | 气泡内出现按专家/任务分类的独立回答卡片 |
| A04 | 同一专家连续追问多轮 | 每轮独立请求与答案；历史可回看，正确接续原调用 |
| A05 | 用户回答一张卡片 | 只恢复对应任务，不重新做总入口意图路由，不取消其他专家 |
| A06 | 同时提交、重复提交、网络重试 | 无重复恢复、无答案丢失；旧版本/过期请求被明确拒绝 |
| A07 | 刷新、断线、后端重启 | 状态和草稿按设计恢复；已接受答案继续执行；事件可重放 |
| A08 | 用户更正共享事实 | 新版本生效；依赖任务发现变化，相关旧结果被复核 |
| A09 | 多孩子、多任务、同专家多子任务 | 事实与局部状态不串用，任务标识明确 |
| A10 | 已回答信息离开近期窗口 | 通过事实/问答账本继续有效，不被旧摘要引导重复询问 |
| A11 | 模型失败或工具超时 | 明确失败/有限重试；不会伪造缺失信息或重新登记问题 |
| A12 | 用户改目标、取消或拒绝补充 | 受影响任务按范围处理；必需信息不足时不伪称最终完成 |
| A13 | Skill 本地资料搜索/Web Search 与挂起恢复 | 来源保留，已完成调用不无故重跑；工具授权与预算生效 |
| A14 | 汇总时仍有必要任务待答 | 主 agent 正确区分阶段反馈和最终结果，保留未解决项 |
| A15 | 与问题对话基线比较 | 重复追问、规则冲突与推进失败有可核查的改善证据 |

每项要求需有对应集成/故障场景或真实模型回放证据，不能仅以单元测试和静态结构证明完成。执行阶段开始后补充测试入口、结果及调用追踪引用。
